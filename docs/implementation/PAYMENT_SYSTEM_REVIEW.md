# Sandbox payment system review

Scope confirmed by the user on 2026-10-04: improve the current PayPal Sandbox system. Live payments and deployment are outside this review. Preserve the deterministic permission boundary, explicit human confirmations, existing design and unrelated local changes.

The review covers proposal/approval ownership, authoritative prices and integer money, spending reservations, order/capture idempotency, provider response validation, signed webhook reconciliation, refunds, recovery, and browser state. Automated provider tests use simulated PayPal; the existing real Sandbox capture/full-refund evidence is tracked separately in PROGRESS.md.

## Corrected findings

The fixes retain explicit human payment/refund confirmation, server-owned product facts, integer USD amounts, signature verification, ownership checks and deterministic AgentGuard decisions. Status checks only read existing provider objects; they do not create orders, capture payments or submit refunds. Existing completed provider outcomes can be recorded after permission expiry, while new financial execution still requires current authorization.

Two existing browser checks also exposed a resize-following issue in chat and an empty Demo Catalog search for a brand alternative such as “Sony or Bose”. Those corrections preserve the existing interface and restrictions. The synthetic shopping fixture now honors early filtering of refurbished products under a NEW-only mandate. Isolated browser account setup uses separate test IPs; a bounded test-only application option accommodates fixture provisioning without changing production authentication limits.

## Provider failure handling, reconcile worker and PAYPAL_ENV (2026-10-12)

PayPal responses are now classified before any state change. Only a parsed PayPal 4xx rejection (other than 401, 408, 409 and 429) is **definitive**: the operation was not performed. Network errors, timeouts, 401/408/409/429, 5xx and malformed bodies stay **uncertain** and keep the existing hold-and-reconcile behavior. From an error body the adapter keeps only `name`, the first `details[].issue` and `debug_id`; messages, descriptions and links are discarded and never stored or logged.

| Outcome                                                     | Recorded result                                                                                                                                                                                                                                          |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture `INSTRUMENT_DECLINED` / `PAYER_ACTION_REQUIRED`     | Payment returns to `APPROVED` with that reason, the capture request ID is rotated (PayPal would replay the cached failure), the proposal returns to `PAYPAL_ORDER_CREATED`, the hold stays active and the order's PayPal redirect is shown to the payer. |
| Capture `ORDER_NOT_APPROVED`                                | Payment returns to `CREATED` (awaiting approval) with a PayPal approval link.                                                                                                                                                                            |
| Capture `ORDER_ALREADY_CAPTURED`                            | The order is read back and its existing capture is recorded; no second capture is sent.                                                                                                                                                                  |
| Any other definitive capture rejection, or a `VOIDED` order | One transaction: payment `FAILED` (`PAYPAL_CAPTURE_REJECTED:<issue>` / `PAYPAL_ORDER_VOIDED`), proposal `FAILED`, reservation `RELEASED`, with audit events.                                                                                             |
| Capture `PENDING` (held)                                    | Payment stays `CAPTURE_PENDING` with its capture ID and `status_details.reason` (for example `PENDING_REVIEW`); the hold is kept.                                                                                                                        |
| Definitive refund rejection                                 | Refund `FAILED` (`PAYPAL_REFUND_REJECTED:<issue>`) with a `REFUND_FAILED` audit, which restores the refundable remainder. Uncertain refund errors stay `SUBMITTED`.                                                                                      |
| Definitive order-creation rejection                         | The order request ID is rotated and the API answers 422 `PAYPAL_REQUEST_REJECTED`; nothing exists at PayPal.                                                                                                                                             |

A capture already in `CAPTURE_PENDING` was authorized when it was claimed. Retrying it replays the same idempotent capture request (or settles from the order) without re-running AgentGuard, catalog or proposal-expiry checks, and a policy re-evaluation never moves a `PAYMENT_PENDING` proposal to `BLOCKED`. Lock order stays User → Mandate → Proposal → Payment.

Webhooks additionally handle `PAYMENT.CAPTURE.PENDING`, `CHECKOUT.ORDER.COMPLETED` (settles from the order's own capture) and `PAYMENT.CAPTURE.REVERSED` (payment `REVERSED`, `PAYMENT_REVERSED` audit; refunds are then blocked). A completed refund issued in the PayPal dashboard for a known capture is re-fetched from PayPal and recorded once as a `providerInitiated` refund, bounded by the captured amount. Signature verification embeds the delivered raw body byte-for-byte in the verify request. Pending webhook outcomes now retry on a long schedule (15 minutes doubling to 6 hours, up to 24 attempts, roughly four days); processing failures keep the five-attempt policy. Customer, admin and worker status checks resolve a `CAPTURE_PENDING` payment from PayPal reads: completed order → settled; voided order → failed and released; still-approved order unchanged for 10 minutes → returned to the payer with the same capture request ID, so the next attempt remains an idempotent replay.

The adapter refreshes the OAuth token and repeats a request exactly once after a 401, retries GETs and keyed POSTs (`PayPal-Request-Id`) after uncertain errors with bounded exponential backoff (`PAYPAL_MAX_RETRIES`, default 2, maximum 5), sends `payment_source.paypal.experience_context` (return/cancel URLs, `PAY_NOW`, `NO_SHIPPING`, brand name) with server-owned line items and an exact `item_total`/`shipping`/`tax_total` breakdown, accepts the `payer-action` redirect, and keeps `invoice_id`/`note_to_payer` on full refunds.

### Payment reconcile worker

`pnpm --filter @mandatepay/api build` then `pnpm --filter @mandatepay/api worker:reconcile` runs one bounded pass (schedule it like `worker:webhooks`). It (a) reconciles `CAPTURE_PENDING` payments unchanged for `PAYMENT_RECONCILE_STALE_MINUTES` (default 10, 1–1440) using only order/capture reads and (b) releases expired `ACTIVE` reservations of unpaid proposals while keeping every hold a capture may still consume. Batches are limited by `PAYMENT_RECONCILE_BATCH_SIZE` (default 50, maximum 500). Each change re-checks state under row locks, so concurrent runs are safe; a run writes a `paypal-payment-reconcile` heartbeat. It never creates an order, capture or refund.

### PAYPAL_ENV

`PAYPAL_ENV=sandbox|live` (default `sandbox`) is mapped in one place (`packages/paypal/src/config.ts`): Sandbox uses `api-m.sandbox.paypal.com` and buyer hosts `www.sandbox.paypal.com`/`sandbox.paypal.com` (unchanged); live uses `api-m.paypal.com` and `www.paypal.com`, and requires HTTPS return URLs. Approval-link and webhook resource-link allowlists derive from it. The browser accepts approval redirects only on `https://www.sandbox.paypal.com` or `https://www.paypal.com`. Live is an explicit opt-in.

Additive migrations `20261012000100_add_payment_failure_recovery` (enum values `REVERSED`/`PAYMENT_REVERSED`, `Payment.providerStatusReason`, `Payment.payerActionUrl`, `Refund.providerInitiated`, `WebhookInbox.awaitingProvider`, a `Payment(status, updatedAt)` index) and `20261012000200_allow_payment_reconcile_heartbeat` were applied to the development and test databases. Evidence: simulated-provider unit and integration tests only; no live PayPal or real Sandbox transaction was performed for this change.
