## Authentication topology and Phase 1 schema

Browser calls relative `/api/admin/*` on the admin Next app. Its fixed, method/path-allowlisted BFF forwards only to configured server `API_URL`; Fastify owns Better Auth and all admin authorization. Admin server rendering calls `/api/admin/me` with forwarded cookies and `cache: no-store`. Never expose an API bearer/session token, database client or payment SDK to browser code. Do not forward admin requests through the customer's proxy, which excludes them.

Use one Better Auth identity store with host-only cookies and a separate sign-in on the admin origin. Production uses HTTPS admin/web origins in the same site; do not set a shared parent-domain cookie or use cross-site browser API calls. Loopback development uses admin `http://localhost:3001` (or its 127.0.0.1 alias), web 3000 and API 4000. Cookies are not isolated by port in loopback development; API authorization must therefore work even when a web session cookie reaches admin. Session presence alone never grants privilege.

Phase 1 adds validated, exact `ADMIN_ORIGIN` configuration. Centralize an allowed-origin set built from APP_URL and ADMIN_ORIGIN; add same-port loopback aliases only outside production. Use that set for Better Auth trusted origins and business mutation checks, with the admin subset required for admin mutations. Configure credentialed CORS for exact WEB_ORIGIN and admin origin/allowed local alias; never wildcard credentials, rewrite a hostile Origin, or trust forwarded host as origin authority. Production fails closed for absent/invalid ADMIN_ORIGIN when admin is enabled. The BFF validates its own Origin before forwarding writes and preserves the original Origin for API validation. Header/content-type/method allowlists and JSON body bounds apply independently of CORS.

| Phase 1 addition     | Required shape and constraints                                                                                                                                                                                                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AdminRole            | Only `ADMIN_SUPER` in v1.                                                                                                                                                                                                                                                                                       |
| AdminPrincipal       | UUID id; unique User FK `userId`; unique `singletonKey="main"` with SQL CHECK permitting only `main`; role ADMIN_SUPER; active boolean; createdAt/updatedAt. This enforces at most one principal even under concurrent bootstrap, including inactive records. No self-registration or role supplied by browser. |
| AdminSessionSecurity | Session FK `sessionId` as primary key, AdminPrincipal FK, createdAt, lastSeenAt, reauthenticatedAt; cascade on Session deletion, index principalId. Only successful credential verification writes reauthenticatedAt. It is not copied from Session.createdAt/updatedAt or a browser timestamp.                 |

Use `MANDATEPAY_ADMIN_USER_ID` only in an explicit idempotent bootstrap command against an existing verified User. Lock/check the singleton; same identity is a no-op, a different identity is a conflict. Do not choose an email or seed credentials. No runtime environment-only grant or second-admin creation endpoint. Recovery/replacement is a later controlled runbook.

If credential sign-in succeeds for a non-admin/unverified/inactive account, revoke that newly created session and suppress its Set-Cookie and raw auth body before returning the generic admin sign-in rejection. Reauthentication must resolve to the current admin identity; credentials for another user never refresh the proof.

`requireAdmin` validates a real Better Auth database session, reloads User and singleton active principal, requires verified email in every environment, and validates the security row belongs to that session/principal. Idle timeout is **30 minutes**, bounded additionally by Better Auth session expiry. Advance lastSeenAt only after successful authorization using an atomic expiry check. On expiry, deny and require credential sign-in; a stale web session cannot renew the row. Fail closed on unavailable database/auth (503). Phase 5 also checks the added User.disabledAt on every access/action. UI guards never substitute for API checks.

Sensitive actions require reauthenticatedAt within **10 minutes**, rechecked immediately before the mutation. Use server-side session-bound proof, not a body `freshAuth=true` flag. Reauthentication requires the current account's credentials via the installed Better Auth credential verification/sign-in API; never compare password hashes in admin code. If sign-in rotates a session, bind security state to the actual returned session and invalidate the old proof. Responses forward HTTP-only Set-Cookie but strip raw auth response tokens. Password reset or session revocation deletes/invalidates proof. Do not persist passwords. No cookie cache, impersonation or admin signup.

Authentication errors: 401 `ADMIN_UNAUTHORIZED` for absent/expired/idle sessions; 403 `ADMIN_FORBIDDEN` for non-admin, inactive, unverified or disabled identities; 403 `ADMIN_REAUTH_REQUIRED` for stale proof. Generic sign-in rejection must not disclose whether an email is an admin. All data and session responses carry `Cache-Control: private, no-store`.

## Common HTTP contract

- Prefix `/api/admin`; GET is read-only. Provider refresh/reconcile uses POST because it may persist authoritative results. Only auth sign-in can be unauthenticated; all operational handlers require `requireAdmin` before queries. Reauth/signout require the current admin session. Strict Zod request/response schemas and explicit Prisma selects are required.
- Lists: `limit` integer 1–100 (default 50), opaque validated `cursor` (max 2048 characters), `q` trimmed max 200 characters, optional owner `userId`, supported enum filters and UTC `from`/`to`. Half-open date interval `[from,to)`, range ≤ 366 days, from < to. Unknown filters/sort keys reject 400. Sorting uses per-resource allowlisted timestamp plus ID tie-break; default newest first except approvals (deadline ascending). Cursor binds sort/filter identity. No offset/page-number promise; UI stores the cursor/filters in URL for bookmark/back navigation.
- Date field: list creation time unless explicitly stated below; approvals use deadline, audit creation, webhook receivedAt. Currency is explicit **USD**, money uses safe integer minor-unit numbers; safely convert Prisma BigInt or return a controlled error. Aggregate overflow must not silently round. Existing User/Session IDs are opaque Better Auth identifiers, not necessarily UUIDs; resource IDs accept bounded letters/numbers/underscore/hyphen strings (1–255 characters), with new admin IDs generated as UUIDs. Provider identifiers occupy separate fields. Dates serialize as UTC ISO strings. Nullable fields mean unknown/absent, not fabricated values.
- List envelope: `{ data: T[], page: { nextCursor: string|null, limit: number }, requestId: string }`. Detail: `{ data: T, requestId: string }`. Relationship collections use their own paginated endpoints/filters, not unbounded arrays embedded in a detail response. Mutation: `{ data: T, changed: boolean, pending: boolean, actionId: string, requestId: string }`; uncertain provider outcomes retain identity and return pending, never asserted success.
- Error: `{ error: { code, message, requestId } }`. 400 invalid schema/reason/confirmation, 401 unauthenticated, 403 authorization/origin/fresh-auth, 404 target missing, 409 state/version/key conflict or retry forbidden, 429 rate limit (Retry-After), 503 dependency/capability unavailable. No stack traces, raw provider messages or upstream auth bodies. Disabled/unimplemented capabilities are omitted from advertised capabilities; they are not empty success endpoints.
- Auth sign-in/reauth: 5 attempts/IP/60s plus existing Better Auth protection. Authorized reads: 120/principal/60s; mutations: 20/principal/60s; financial/recovery: additional 5/principal/60s. Separate bounded buckets, capacity 2048, fail closed at capacity and Retry-After. Per-process initially, one API replica; shared storage required before scaling. Existing customer URL matcher does not cover admin endpoints.
- Every action accepts a trimmed reason (1–255 characters), server-validated confirmation when required, and a stable UUID `requestKey`. State-changing domain requests additionally require the expected state/version (or canonical updatedAt timestamp where no version exists). Server compares inside the domain lock, not just before calling it. Retries with a changed target/body reject 409. Refund keys reach the existing refund service; other actions need durable Phase 2 action/audit correlation before controls ship.
- Medium-risk actions need confirmation. High-risk actions need typed confirmation and fresh auth (user disable, mandate revoke/pause if enabled, new refund, critical setting changes). Client dialogs aid review; server checks enforce it. Status/reconciliation actions also require reason/audit even when a dialog is unnecessary.
- Privileged intent and terminal/pending outcome are correlated in append-only AdminAuditEvent. Local mutations and success audit must commit atomically; existing services with internal transactions need a transaction-aware adapter before enabling an action. Provider calls cannot share a database transaction: persist intent, use stable domain keys, then append the verified/pending/failure outcome. Never equate an intent audit with completed financial execution.

Implemented Phase 2 audit filters are exactly `action`, `targetType`, `targetId`, `actorAdminId`, `result`, `correlationId`, `from`, `to`, `limit`, `cursor`; there is no `q`, owner filter or custom sort. Target ID requires type; dates require paired UTC bounds. Newest creation time/ID ordering and HMAC cursors bind all filters and limit, using the server-only auth secret. Audit list/detail API envelopes additionally include correlationId; API/BFF return validated UUID `x-request-id` and `x-correlation-id` headers. Incoming request IDs are ignored, optional correlation IDs validated, and neither grants authority. All reads use existing admin authorization and read limits. The BFF permits only bounded GET/HEAD audit routes and projects each DTO again.

AdminAuditRepository accepts the domain transaction client for append plus readonly search/detail. AdminActionRepository supplies locked idempotent claims and outcome recording with the original correlation ID; it executes no domain control. Session successes append atomically with proof creation/rotation/revocation; credential failures store fixed reasons and anonymous or currently verified actors without submitted identifiers. The reason helper rejects recognizable credential material but cannot infer every secret hidden in ordinary prose. Future adapters must collect safe explanations and use approved summary fields rather than serialize request/provider payloads.

No unbounded all-record export or browser-side dataset aggregation. These export endpoints are implemented for the Phase 4 resources above.

## Metric definitions and availability

`/overview` returns `{ data: { asOf, range:{from,to}, currency:"USD", metrics, controls, warnings }, requestId }`. Each metric is `{ value:number|null, availability:"available"|"unavailable", reason:string|null, definition:string }`. Counts and amounts have distinct names/units. Current-state counts are as-of; flow counts use the stated range; monetary charts use capture/settlement time, not record updates. Do all aggregation on the API/database.
