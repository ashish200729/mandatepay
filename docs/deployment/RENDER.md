# Optional Render deployment

Hosted deployment and live Sandbox buyer verification were deferred by the user. No services have been created. The root `render.yaml` is a reviewable configuration template, based on [Render's Blueprint reference](https://render.com/docs/blueprint-spec), with paid compute plans and automatic deploys disabled.

When hosting is resumed, import the public repository as a Blueprint. It defines a Next.js web service, Fastify API, PostgreSQL 17 database and a scheduled webhook recovery job in the same region. Builds remain at the monorepo root so shared packages and the lockfile are available. The API pre-deploy command applies migrations; failed migrations must stop deployment. Validate the Blueprint in Render before creating billable services.

The web service receives only `API_URL` and `APP_URL`. API credentials are configured as protected service environment values. Configure a verified Resend sender and `RESEND_API_KEY` / `AUTH_EMAIL_FROM`; production authentication fails closed without verified-email delivery. Sandbox credentials remain server-side. Do not copy local `.env` files into source or build artifacts. Use complete public HTTPS URLs when adding custom domains, and update both `APP_URL` and `WEB_ORIGIN` together.

After the API is healthy, register `https://<api-host>/api/webhooks/paypal` in the same PayPal Sandbox REST app. Subscribe to order-approved, capture-completed, capture-denied and capture-refunded events, then set `PAYPAL_WEBHOOK_ID`. Use a separate personal Sandbox buyer and record the actual order, capture, refund and verified webhook results. Do not count the injected test transport as a live financial demonstration.

The recovery cron runs `pnpm --filter @mandatepay/api worker:webhooks`. It reads only previously verified durable inbox records, claims database leases, fetches authoritative provider state and retries with bounded backoff. It never creates or captures a payment. Five total processing attempts are allowed by default; exhausted records remain visible in the database for investigation. The worker prints aggregate counts without payloads or credentials. Monitor job failures, exhausted events, database health and pending financial outcomes.

The synchronous purchase flow remains in the API because human review and checkout are interactive. This template uses Render Cron Jobs, not the Render Workflows SDK. Do not describe Render Workflows as integrated or hosted acceptance as passed. Unknown order/capture/refund outcomes retain reservations and must be reconciled through the existing idempotent endpoints or verified events; never release holds merely because a timeout elapsed.

Before opening a hosted demo: run the full checks, migrations and browser workflow from a fresh clone; verify HTTPS cookies, signup verification, password reset/session invalidation, cross-user denial, duplicate capture/refund protection, real webhook delivery and a recovery retry. Configure backups and alerting. The in-memory request limiters assume a single API replica; add shared limits before scaling replicas. Keep Vault, live payments, recurring purchases and voice disabled until their separate implementation and consent gates are met.
